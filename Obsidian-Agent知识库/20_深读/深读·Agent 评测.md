# Agent 评测

> 深读卡 · 锚点 [[Agent 评测]] · 从「监控绿灯」到「数字过关」的完整机制

> [!abstract] 一句话
> 评测是整张图里最容易被当成「上线前跑一遍」的环节，也是唯一能回答「答案对不对」的环节。监控告诉你系统还活着，评测告诉你它还说得对。这两件事在任何指标上都不重叠。

## 01 · 内部结构：一条闭环，不是一个环节

九阶段看着像九件拼装的工具，实际上是「时机 × 目的」的展开。理解组合逻辑后，你可以为自己的场景重新推导阶段，而不是照抄。

| 环节 | 说明 |
|---|---|
| **1 地基** | 先定义「什么叫好」：业务指标 → 评测指标 → 失败分类法 → 评测器栈 → 黄金集。顺序不能反。 |
| **2 实验** | 每次变更在同一黄金集上跑，五维并排比。准确率 +5% 但延迟翻倍，不算赢。 |
| **3 CI** | 每次部署自动跑哨兵集（15 条高危场景），分钟级。质量/安全硬阻断，延迟/成本软阻断。 |
| **4 CD 门禁** | 全量黄金集 + 工具 mock 回放 + 200 题端到端。三条任一触发即关门。 |
| **5 金丝雀** | 生产侧每 30 分钟一轮，轮转覆盖、24h 全量；连续 3 窗口越界才 page。 |
| **6 对抗** | 入口与出口各拦一次，100% 流量。越狱、注入、泄露三类子问题。 |
| **7 漂移** | 采样 10% 真实流量打分，与离线基线比对。抓「没人改代码」的劣化。 |
| **8 脉搏** | OTel 轨迹 + 评测分数两条管道，落到同一时间窗。分数必须能一键跳到具体 trace。 |
| **9 反馈** | 低分 trace 晋升为永久回归守卫。让失败只发生一次。 |

> 虚线是这套东西之所以「闭环」的原因：每条回流路径都必须把线上教训变成下一次的考题。没有回流，九阶段只是九个检查点。

## 02 · 五个绕不开的决策

这些决策没有标准答案，但有明确的取舍方向。选错不会立刻报错，会在半年后以「评测数字没人信」的形式暴露。

### 单一准确性指标，还是失败分类法？

**结论：** 分类法。

「准确率 87%」无法指导任何行动——你不知道那 13% 错在哪。拆成「指标取错 / 周期错配 / 实体混淆 / 纯幻觉 / 单位错误 / 未授权计算」后，每一类都能配一个专属评测器，指标才变得可行动。

> [!warning] 代价
> 前期要把真实错误手工归类，通常需要看几百条坏样本。

### 全量题集，还是分层（哨兵 + 黄金集）？

**结论：** 分层。

速度与覆盖不可兼得。全量跑一次几十分钟，不可能每次提交都跑；只跑全量又会让回归漏到发布前。哨兵管「每次」，黄金集管「发布前 / 每日」。

> [!warning] 代价
> 哨兵集只能防已知的致命错误，不能证明没有新错误——它通过不等于是充分条件。

### 确定性断言，还是 LLM 当裁判？

**结论：** 双轨，不是二选一。

确定性评测给事实以精度（金额、日期、实体、SQL 结果集），LLM 评审给推理以广度（相关性、忠实度、切题）。让模型判断「410.08 和 410.08 Million 是否一致」，它经常答错。

> [!warning] 代价
> 两套都要维护，且 LLM 裁判必须单独校准一致率，否则偏差会系统性地进入所有指标。

### 工具实时调用，还是 mock 回放？

**结论：** 发布门禁用回放。

先单独验证工具正确，把已验证的答案冻结成回放集，再让 Agent 在冻结世界里跑。这样 head-to-head 的差异只归因于 Agent 本身，不受工具快慢与可用性干扰。

> [!warning] 代价
> 回放屏蔽了「工具变慢 / 超时 / 部分失败」这类真实故障模式，只能靠生产侧金丝雀补。

### 单窗口告警，还是连续多窗口？

**结论：** 连续 3 窗口。

单窗口阈值会让 on-call 被噪声淹没，最后彻底不再信任系统。降阈值到「信号」级别 + 连续 3 窗口越界才 page，是用「告警被忽略」换来的教训。

> [!warning] 代价
> 发现延迟从 30 分钟变成 90 分钟。这是刻意的取舍。

## 03 · 失败模式：评测系统自己会怎么坏

评测是一套测量装置，它自己也会失准。下面六种是最常见的，且多数不会被指标本身发现。

### 题集只装「能答对的题」

评测失去区分度，所有版本都是 95%。必须有意识地塞入 20% 已知会错的、20% 边界模糊的。

**修法：** 建集时就按失败类型配额，而不是按场景抽样。

### 裁判与人对不上

rubric 太抽象，或裁判模型不适配领域。0.8 一致率以下，所有数字都不可信。

**修法：** 抽 50–100 条人工标注做校准集；不一致就改 rubric，不要改阈值。

### 用同一份集子既优化又验收

Goodhart 效应下指标一路上涨，真实长尾持续退化。提示词自动优化里这几乎是默认做法。

**修法：** 保留一批不参与优化的 holdout 集，只在发布决策时打开。

### 只测均值不看长尾

把均值拉高但更多单题不及格的版本会顺利通过。

**修法：** 门禁同时卡「单题及格率」，而不只是聚合分。

### 小样本上的假提升

200 题样本里 96% 与 96.5% 的差异，大概率是噪声。

**修法：** bootstrap 算置信区间；门禁判据写成「显著优于基线」而非「数值大于基线」。

### 评测成本失控

30 分钟一轮 batch + 10% 线上全量打分，评测开销可能接近甚至超过被评测系统。

**修法：** 评测 token 单独计量、进预算；抽样率按分数方差动态调整。

## 04 · 上手路径：七周最小闭环

目标不是一次做全，而是先做出一次真实的拦截。一次真实拦截比任何指标表都能说服人。

| 阶段 | 动作 | 产出 |
|---|---|---|
| **第 1 周** | 写 3–5 条业务成功标准；枚举本域 5–8 类失败模式并写下判定口径。 | 一页纸质量契约 + 失败分类表 |
| **第 2 周** | 从真实日志抽 100–200 条，标注期望答案，建 v0 黄金集（含安全、延迟、成本基准）。 | 版本化 golden set v0 |
| **第 3 周** | 搭评测器栈：2–3 个内置 + 每类失败一个自定义 + 关键事实用确定性断言。 | 可复现的评测流水线 |
| **第 4 周** | 接 CI：每次部署跑 15 条哨兵，四类条件拦截。 | 自动发布门禁 |
| **第 5–6 周** | 接生产：30 分钟窗口 batch + 10% 采样；告警打通到 trace；连续 3 窗口才 page。 | 生产监控闭环 |
| **第 7 周起** | 建回流：低分 trace → 黄金集，失败 → 永久守卫。 | 自我改进飞轮 |

> 路线一句话：先定义「好」，再造「考卷」，再把考卷接进流水线，最后让考卷自己长大。

## 相关概念

- [[黄金集]] — 版本化的评测题集，含标准答案与判定口径，是判断回归的唯一依据。
- [[哨兵集]] — 从黄金集中挑出的十几条最高危场景，每次部署都跑，分钟级完成。
- [[LLM 评审]] — 用模型按预先写好的评分标准（rubric）给回答打分，覆盖没有唯一正确答案的质量维度。
- [[失败分类法]] — 从真实生产错误反推出的一套互斥的失败类型清单，每类配独立判定口径与评测器。
- [[评测三层级]] — 工具级、单 Agent 级、多 Agent 级各有一套黄金集、评测器与晋级标准，三层都要跑。
- [[确定性评测]] — 对有唯一正确答案的部分（金额、日期、实体、SQL 结果集）用精确断言判定。
- [[裁判校准]] — 定期测量模型裁判与人工标注的一致率，低于阈值就改 rubric，而不是改阈值。
- [[回归门禁]] — 每次部署自动跑哨兵集，质量、安全、延迟、成本任一维度越界则阻断发布。
- [[漂移检测]] — 持续采样线上真实流量并打分，与离线基线比对，发现无代码变更下的质量滑坡。
- [[评测过拟合]] — 系统被调成「专门讨好评测集」的样子，分数一路上涨，真实使用反而变差。
