# 工具定义

> **L3.P4 · 工具层 / 行动** · 机制·质量面 · 核心 / 稳定

**Tool Definition**  ·  别名：工具 schema、函数签名

## 一句话

用名称、描述、参数 schema 声明一个可被模型调用的能力。

## 具体是什么样

> {"name":"query_order","description":"按订单号查状态；只在用户提供了订单号时使用","parameters":{...}}

## 看不懂？先看这几个

- [[原生工具调用]] — 模型直接输出结构化调用指令，而非在自由文本里夹带「我想调用某函数」的意图。

## 它解决什么问题

模型无法调用未声明的东西，也无法正确填写描述含糊的参数。

## 它新在哪

看似简单，但它是 Agent 里 ROI 最高的文本：锐化一句工具描述，常常比调十轮 prompt 有效。

## 被谁继承

- [[工具返回设计]] — 决定工具返回什么、返回多少、失败时怎么说——这直接决定了模型的下一步判断质量。
- [[工具选择]] — 在给定任务与可用工具集下，选出正确的工具与正确的参数。
- [[代码解释器]] — 让模型写代码并在隔离环境中执行，用代码代替自然语言做精确计算与数据处理。
- [[OpenAPI 转工具]] — 把已有的 OpenAPI / Swagger 规范批量转成模型可调用的工具定义。
- [[ReAct 范式]] — 把推理（Reasoning）与行动（Acting）交织在同一串 token 里，让观察结果实时修正推理。

## 关联概念

- [[原生工具调用]] — 模型直接输出结构化调用指令，而非在自由文本里夹带「我想调用某函数」的意图。
- [[结构化输出]] — 强制模型只输出符合约定格式的 JSON 等结构，程序可以直接解析，不用从文本里抠。
- [[程序记忆]] — 把成功的操作序列沉淀为可复用的「怎么做」，下次直接调用而不重新探索。
- [[模型上下文协议]] — 把「模型 ↔ 外部能力」的接入方式标准化：一次实现服务端，任何兼容 MCP 的客户端或 Host 都能用。

## 常见误判 / 坑

> [!warning] 坑
> 写面向人类的描述（「查询客户信息」）而不是面向选择的描述（何时用、何时不用、与相邻工具的区别）。
