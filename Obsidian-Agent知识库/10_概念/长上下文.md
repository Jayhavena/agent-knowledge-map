# 长上下文

> **L0.P2 · 模型层 / 取景** · 质量·成本面 · 进阶 / 争议

**Long Context**  ·  别名：百万上下文、context window 扩展

## 一句话

单次可容纳十万至百万 token 的上下文窗口，把「先检索再喂」换成「全部塞进去」。

## 具体是什么样

> 300 页产品手册整个塞进上下文，直接问「第 12 章写的保修期是多久」，跳过检索这一步。

## 看不懂？先看这几个

- [[基础大模型]] — 通过大规模预训练获得通用语言理解与生成能力的模型，是 Agent 唯一的「思考引擎」。

## 它解决什么问题

复杂检索管线本身有工程成本与召回损失；直接全量输入可绕过整条链路。

## 它新在哪

让一部分 RAG 变得不必要——但仅在「可全量装入且注意力分布均匀」时成立，两个条件经常同时不成立。

## 谱系

- **演进** · 上下文窗口（LLM 基础，图外旧概念）
- **替代** · [[检索增强生成]]

## 被谁继承

- [[上下文腐化]] — 上下文越长，模型对其中任意一条信息的利用率越低，且错误更倾向于「看起来合理」。

## 关联概念

- [[基础大模型]] — 通过大规模预训练获得通用语言理解与生成能力的模型，是 Agent 唯一的「思考引擎」。
- [[上下文压缩]] — 在长会话或多轮工具调用中，把历史压缩成摘要或摘要+关键原文，控制 token 增长。
- [[中间遗忘]] — 模型对长上下文首尾两端的召回显著优于中段，呈 U 形曲线。
- [[大海捞针测试]] — 在超长文本的随机位置埋入一个事实，考察模型能否准确取出。
- [[提示缓存]] — 把稳定前缀（系统提示、工具清单、长文档）的计算结果缓存，后续请求直接复用。
- [[检索增强生成]] — 先从外部知识库检索相关片段，再连同问题一起送入模型生成答案。

## 常见误判 / 坑

> [!warning] 坑
> 把标称窗口当可用容量。中间遗忘与成本线性增长，会让「全塞」在实际业务里更差。
